# tech-deck — 기술서 → 발표 deck

> **공통 규약을 먼저 읽는다** → [`_common.md`](_common.md)

스터디·사내 발표용 슬라이드. **압축이 아니라 재구성**이다 —
기술서를 줄이면 목차만 남는다. 코드·용어·절차는 살리고 **순서를 청중에 맞게 바꾼다.**

옵션: `level` · `examples` · `density` · `minutes`

## ① 아웃라인 — 슬라이드 수를 먼저 정한다

**슬라이드 수는 시간에서 역산한다.** 내용에서 올라오게 두면 항상 두 배가 된다.

```
목표 슬라이드 수 = round(minutes × 0.8)        # 20분 → 16장, 45분 → 36장
density simple  → × 0.7   standard → × 1.0   full → × 1.4
```

그 수를 이렇게 나눈다 — **표지·목차·마무리를 먼저 떼고 남는 것이 본문 몫이다.**

| 칸 종류 | 수 | `chapterId` |
|---|---|---|
| 표지 | 1 | null |
| 왜 이 책인가 — 어떤 문제를 푸는 책인지 | 1 | null |
| 흐름 — 발표 순서 (장 순서가 아니다) | 1 | null |
| **본문** | 남는 전부 | 장마다 1개 이상 |
| 한 장으로 — 핵심 3줄 | 1 | null |
| 더 읽을 것 | 0~1 | null |

### 장 하나짜리 deck 이면 — 배분 대상이 **절**이다

`put_outline(chapterId=...)` 로 범위를 한 장에 걸었다면 위 표의 '본문' 을 **그 장의 절**로 나눈다.

```
목표 슬라이드 수는 똑같이 시간에서 역산한다 (장 하나라고 줄이지 않는다)
        ↓
그 장의 절(3.1 · 3.2 …)에 가중치를 준다 — 이 장의 핵심 주장이 있는 절 > 설명 절
        ↓
절 하나에 1~4슬라이드. 절이 모자라면 예시·코드로 채운다 (슬라이드를 비우지 않는다)
```

🔴 **다른 장을 끌어오지 않는다.** "3장 발표자료" 인데 5장 내용이 들어가면 듣는 사람의 전제가
깨진다. 필요하면 "2장에서 본 것" 처럼 **가리키기만** 한다 — `sourceChapters` 에도 그 장만 넣는다.

**본문 배분 — 균등하게 나누지 않는다.**

1. 목차에서 **발표 주제에 닿는 장만 고른다.** 50장 책에서 16장짜리 발표면 장을 버려야 한다.
   버리는 것이 기획이다 — 전 장을 1슬라이드씩 넣으면 아무것도 전달되지 않는다
2. 고른 장에 가중치를 준다: 이 책의 **고유한 주장**이 있는 장 > 설명 장 > 참고 장
3. 가중치대로 슬라이드를 나눠 준다 (한 장에 1~4슬라이드)

각 칸의 `plan` 에 **무엇을 주장할지**를 쓴다. "3장 요약" 이라고 쓰지 않는다 —
`"3장: 클로저는 메모리 누수의 원인이 아니라 스코프 설계 도구다 (반례 2개)"` 처럼 쓴다.

> 🔴 아웃라인을 사람에게 보일 때 **버린 장을 함께 말한다.** "12·14·19장은 발표 주제 밖이라
> 뺐습니다" 라고 하면 사람이 되돌릴 수 있다. 말없이 빼면 빠진 걸 아무도 모른다.

## ② 칸 채우기 — 슬라이드 하나는 주장 하나다

칸마다 `get_chapter_text(chapterId)` → 그 장만 받아 그 칸만 쓴다.

## 🔴 `note` 에 메타 발언을 쓰지 않는다

`<p class="note">` 는 **발표 중 질문에 답할 근거**(어느 장에서 왔나)를 적는 자리다.
그런데 2026-10-05 에 만든 세 덱이 전부 이렇게 나갔다:

```
❌ 출처: 10장 · 347~404쪽 · 이 발표는 10장 안에서만 인용한다
❌ 1~76쪽 · 이 발표는 1장 안에서만 인용한다
```

**듣는 사람에게 아무 쓸모가 없다.** 쪽 범위는 발표자가 알면 되는 것이고,
"이 발표는 N장 안에서만 인용한다" 는 **작성자가 스스로에게 건 규칙**이지 청중에게 할 말이 아니다.
`_common.md` 의 *"메타 발언 금지"* 가 이미 있었는데 지키지 않았다.

```
⭕ 출처: 10.4 조건부 로직을 다형성으로 바꾸기
⭕ 출처: 6.2 · 오버라이드되는 메서드는 인라인하지 않는다
```

판정 한 문장 — **"이 줄이 듣는 사람의 이해를 돕는가, 아니면 내 작업 범위를 설명하는가."**
후자면 지운다.

## 슬라이드 원형을 섞는다 — 16장이 같은 모양이면 실패다

전 슬라이드가 `<h2>` + 불릿 4개면 **발표자료가 아니라 요약본**이다(2026-10-05 실제).
원형과 배합은 [`../references/deck-patterns.md`](../references/deck-patterns.md) 가 정본이다.

## `visuals` — 그림을 몇 장 넣나

| `visuals` | 16장 기준 | 무엇을 그리나 |
|---|---|---|
| `none` | 0장 | 글로만. 구조 설명이 없는 주제일 때만 |
| `some` (기본) | **3~5장** | 흐름 1 · 전후 비교 1 · 구조나 비율 1 |
| `many` | 6~8장 | 위 + 묶음마다 하나 |

🔴 **외부 이미지를 불러올 수 없다.** 인라인 SVG·CSS 박스로 그린다 —
[`../references/visual-vocabulary.md`](../references/visual-vocabulary.md) 에 쓸 수 있는 조각이 있다.
`<pre>` 안 ASCII 아트로 때우지 않는다(발표 화면에서 줄이 깨지고 키울 수 없다).

## `tone` — 얼마나 친근하게

| `tone` | 비유·사례 | 가벼운 한 줄 |
|---|---|---|
| `plain` | 책 안 예시만 | 없음 |
| `light` (기본) | 익숙한 서비스 비유 **1~2개** | 1~2회 |
| `vivid` | 장면으로 열고 비유를 축으로 | 3~4회 |

실제 서비스 사례 고르는 법과 **지어내지 않는 규칙**은
[`../references/tone-and-hooks.md`](../references/tone-and-hooks.md).
🔴 그 회사가 실제로 그렇게 구현했다고 **단정하지 않는다** — "이런 화면이라면" 처럼 가정으로 말한다.

**슬라이드 골격**

```html
<section>
  <h2>주장 한 문장</h2>          <!-- 제목이 아니라 주장. 장 제목 복사 금지 -->
  <ul>
    <li>근거 · 사실 (2~4개)</li>
  </ul>
  <p class="note">출처: 3장</p>   <!-- 어느 장에서 왔는지. 발표 중 질문에 답하는 근거 -->
</section>
```

**분량 상한 — 넘기면 잘려 사라진다** (`overflow: hidden`)

| | 상한 |
|---|---|
| `<h2>` | 40자 |
| `<li>` | 4개 · 각 60자 |
| `<pre>` | 14줄 · 각 70자 |

넘칠 것 같으면 **슬라이드를 쪼개는 게 아니라 덜 말한다.** 쪼개면 아웃라인 계약이 깨진다.

> 🔴 **칸의 주장이 본문에 없을 때 — 칸을 늘리지 말고 그 칸의 주장을 바꾼다.**
> 아웃라인은 ①에서 **목차만 보고** 쓴다. 그래서 장 제목에서 짐작한 주장이 본문에 없는 일이
> 생긴다 (2026-10-03 실제: "11장: 공개된 것을 바꿀 때 점진·병행" 으로 승인받았지만 11장은
> 명령-질의 분리·플래그 인수 제거였고, `점진적 교체` 는 7장의 주장이었다).
> 그 장이 **실제로 하는 말**로 바꿔 쓰고, 승인본과 달라진 점을 사람에게 한 줄로 말한다.
> 원문에 없는 주장을 그대로 채우면 **근거 없는 슬라이드**가 되고, 칸을 늘리면 계약이 깨진다.

**코드 슬라이드** (`examples` 가 `some`·`many` 일 때)

- 🔴 **코드는 원문 그대로다.** 요약하거나 "..." 로 줄이지 않는다 — 안 돌아가는 코드가 된다
- 14줄을 넘으면 **코드를 줄이지 말고 핵심 부분만 발췌**하고, 발췌임을 `note` 에 적는다
- 코드 슬라이드 다음에는 **"그래서 무엇인가" 슬라이드**를 둔다. 코드만 띄우면 아무도 안 읽는다

**`level` 별 차이**

| | `intro` | `working` | `deep` |
|---|---|---|---|
| 용어 | 등장할 때마다 한 줄 정의를 붙인다 | 처음 한 번만 | 전제한다 |
| 전제 | "이걸 모르면 안 됨" 슬라이드를 앞에 둔다 | 생략 | 생략 |
| 깊이 | 왜 필요한지에 무게 | 어떻게 쓰는지 | 함정·트레이드오프·내부 동작 |
| 예시 | 가장 단순한 것 하나 | 실무형 | 경계 조건·실패 사례 |

## ③ 조립

1. **표지** — 책 제목·저자, 그리고 **이 발표의 한 줄**(책 소개가 아니다)
2. **흐름 슬라이드**를 실제로 채워진 본문 순서로 맞춘다 (②에서 바뀌었을 수 있다)
3. **전환 점검** — 슬라이드 n 의 주장과 n+1 의 주장이 이어지는가. 안 이어지면 한 줄 다리를 놓는다
4. **한 장으로** — 핵심 3줄. 본문에서 가장 많이 반복된 주장을 고른다
5. `countSlides` 가 아웃라인 칸 수와 같은지 확인한다. 다르면 ②에서 쪼갰거나 합친 것이다

## 금지

- 🔴 **`note` 에 메타 발언·쪽 범위** — 듣는 사람에게 쓸모가 없다 (2026-10-05 에 세 덱이 다 걸렸다)
- 🔴 **전 슬라이드 같은 모양** — 원형을 섞는다 (`references/deck-patterns.md`)
- 🔴 **그림 0장** — `visuals: none` 을 사람이 고른 게 아니면 최소 3장
- 장 제목을 슬라이드 제목으로 복사 — 제목은 주장이다
- 전 장 균등 배분 — 버리는 것이 기획이다
- 코드를 요약·생략하는 것 (`...`) — 안 돌아가는 코드
- 한 슬라이드에 주장 두 개
- `examples: none` 인데 코드 슬라이드를 넣는 것
