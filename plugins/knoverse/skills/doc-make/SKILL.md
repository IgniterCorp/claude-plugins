# doc-make — 책 → 발표자료·핸드아웃·독후감 (제품에 적재)

> 산출물은 노버스 콘솔 **책 상세 › 문서 탭**에 쌓인다. deck 은 슬라이드쇼로 뜨고
> 다운로드하면 PDF 가 된다.

## 🔴 이 스킬의 전제 — 생성자는 너다

서버에 생성 기능이 **없다.** MCP 에 `generate_*` 툴이 없는 것이 설계다 —
서버가 만들면 제로클라우드 AI 리소스를 타고 장당 과금된다. 어떤 템플릿·옵션이 쓸 만한지
모르는 단계라 그 실험비를 과금으로 치르지 않는다.

**그래서 본문을 쓰는 것은 이 세션이다.** 서버는 받아 저장한다.

## 전제 확인

MCP 서버 `knoverse` 가 붙어 있어야 한다 (`mcp__knoverse__*` 툴).
원격 서버(`https://api.knoverse.im/mcp`)다. 안 보이면 **포기하기 전에** `claude mcp list` 로 등록 여부를 본다.
없으면 콘솔 「설정 › MCP 연결」에서 `kn_mcp_` 토큰을 받아 `claude mcp add` 한다(이 플러그인 README).
401 이면 콘솔에서 토큰이 폐기됐는지 본다.

## 0. 무엇을 만들 것인가

1. `find_books(q)` 로 책을 찾는다. 여러 개면 **사람에게 고르게 한다** — 엉뚱한 책으로
   만들면 ②까지 다 돌고 나서야 안다
2. `list_templates()` — 5종이 온다. `kind` 가 `deck`(발표) · `handout`(핸드아웃) · `doc`(독후감)
3. 🔴 **고른 템플릿의 플레이북을 Read 로 읽는다.** 그 문서가 절차의 정본이다.
   MCP 는 `playbook`(이 플러그인 기준 상대경로 — 예 `skills/doc-make/playbooks/deck.md`)을 준다. 플러그인 루트 아래에서 읽는다.
   `MISSING:` 으로 시작하면 **멈추고 사람에게 말한다** — 절차 없이 쓰면 안 된다
4. `playbooks/_common.md` 도 읽는다 (HTML/CSS 계약·공통 금지가 거기 있다)
5. 🔴 **`references/` 를 읽는다** — `deck-patterns.md`(슬라이드 원형·배합) ·
   `visual-vocabulary.md`(그림 그리는 법) · `tone-and-hooks.md`(톤·실제 사례).
   플레이북이 *지켜야 할 것*이면 레퍼런스는 *좋은 것의 모습*이다. **둘 다 읽어야** 한다 —
   상한만 지키면 요약본이 나온다 (2026-10-05 에 실제로 그랬다)

## 🔴 옵션을 묻기 전에 `put_outline` 을 부르지 않는다

**이 규칙이 이미 있었는데 내가 건너뛰었다** (2026-10-05). deck 세 개를
`level: working` · `examples: many` · `minutes: 20` 으로 **아무에게도 안 묻고** 만들었다.
난이도는 듣는 사람이 누구냐를 정하는 축인데 그걸 내가 혼자 골랐다.

그래서 순서를 못으로 박는다 — **묻기 → 답 받기 → 받은 값을 되읽어 주기 → `put_outline`.**

`list_templates` 가 준 `options` 의 `label`·`choices`·`hint` 를 **그대로 읽어 준다.**
**선언에 없는 옵션을 발명하지 않는다** (서버가 거절한다). 2026-10-05 기준 `tech-deck` 은 여섯이다:

| 옵션 | 묻는 문장 (예) |
|---|---|
| `level` 난이도 | "듣는 사람이 이 분야를 아나요? intro(용어를 매번 풀어줌) / working / deep(전제함)" |
| `minutes` 시간 | "몇 분이에요? 20분이면 16장쯤 됩니다" |
| `density` 밀도 | "슬라이드를 촘촘히(full) 할지 여유 있게(simple) 할지" |
| `examples` 예시·코드 | "코드를 얼마나 실을까요? none / some / many" |
| **`tone` 톤** | "톤은요? plain(사실만) / light(익숙한 서비스 비유 1~2개) / vivid(장면으로 열고)" |
| **`visuals` 그림** | "다이어그램을 넣을까요? some 이면 16장 중 3~5장이 그림이 됩니다" |

| 묻는 법 | 안 묻는 법 |
|---|---|
| 여섯을 **한 번에** 보여 주고 기본값을 밝힌다 | "옵션 알려주세요" |
| "20분이면 16장쯤 됩니다" 처럼 **결과를 같이** 말한다 | 슬라이드 수를 직접 물어보기 |
| 받은 값을 **되읽어 주고** 시작한다 | 말없이 기본값으로 진행 |

**사람이 "알아서 해" 라고 하면** 기본값으로 가되 **무엇으로 갔는지 한 줄로 말한다.**
말없이 고르는 것과 다르다 — 그래야 아웃라인 승인 단계에서 되돌릴 수 있다.

## 범위 — 책 전체인가, 한 장인가 (2026-10-04)

**맨 처음 묻는다.** `put_outline` 의 `chapterId` 가 범위를 정한다.

| | `chapterId` | 아웃라인이 다루는 것 | 쓸 때 |
|---|---|---|---|
| **책 전체** | 비운다 | 장을 **골라서** 버린다 (버리는 것이 기획이다) | 책 한 권을 한 번에 발표 |
| **한 장** | 그 장 id | 그 장 **안**의 절로 칸을 나눈다 | 장마다 돌아가며 발표 · 스터디 한 주치 |

🔴 **장 범위에서 다른 장을 끌어오지 않는다.** "3장 발표자료" 인데 5장 내용이 들어가면
듣는 사람의 전제가 깨진다. 필요하면 "2장에서 본 것" 처럼 **가리키기만** 한다.

🔴 **슬라이드 수는 장 범위에서도 시간으로 역산한다.** 장 하나라고 줄이지 않는다 —
20분이면 16장이고, 그 16장을 한 장(章) 안에서 채운다. 절이 모자라면 예시·코드를 더 쓴다.

콘솔 문서 탭이 **책 전체와 장별을 갈라서** 보여 준다(범위 칩). 목차가 통째로 교체돼 그 장이
사라져도 문서는 남고 **'장 없음'** 으로 뜬다 — 그때는 범위를 다시 정해 새로 만든다.

## 1. ① 아웃라인 — 체크리스트가 계약이다

`get_book_context(itemId)` → 책 메타 + 목차 트리 + 쪽/요약 진행 상황.

🔴 **`chaptersWithoutPage` 를 먼저 본다.** 쪽 없는 장은 `get_chapter_text` 가 거절한다
(범위를 모르면 옆 장 본문을 섞기 때문). 아웃라인에 그 장을 넣기 전에 사람에게 말한다 —
`chapters/suggest-pages` 로 채우면 쓸 수 있다.

플레이북의 칸 배분 규칙대로 체크리스트를 만든다. 각 칸의 `plan` 은 **무엇을 주장할지**다 —
`"3장 요약"` 이 아니라 `"3장: 클로저는 메모리 누수 원인이 아니라 스코프 설계 도구다"`.

**사람에게 보일 때 세 가지를 같이 말한다**

1. 칸 목록 (번호 · 장 · 무엇을 쓸지)
2. **버린 장** — "12·14·19장은 발표 주제 밖이라 뺐습니다". 말없이 빼면 빠진 걸 아무도 모른다
3. 칸 수와 그 근거 ("20분 × 0.8 = 16장")

승인(또는 수정) 받은 뒤 `put_outline(...)` → 문서 `id` 를 받는다. **승인 전에 부르지 않는다.**

## 2. ② 장별 채우기 — 칸 하나 = 생성 한 번

```
칸마다:  get_chapter_text(itemId, chapterId)
         → 플레이북 규칙대로 그 칸만 쓴다
         → put_document(id, status='drafting', body=지금까지의 HTML 전체,
                        outline=그 칸 filled:true, sourceChapters=[...쓴 장])
```

🔴 **칸마다 저장한다.** 다 쓰고 한 번에 올리면 중간에 끊겼을 때 전부 날아간다.
저장이 곧 재개 지점이다.

🔴 **`get_chapter_text` 의 `source` 를 보고 쓰는 법을 바꾼다.**

| `source` | 뜻 | 어떻게 |
|---|---|---|
| `summary` | 이미 요약된 글 | **더 깎지 않는다.** 재구성·재배치만 |
| `pageText` | 장 본문 원문 | 골라내고 깎는다. 없는 걸 지어내지 않는다 |

`pages` 가 범위보다 **훨씬 적으면** 그 장은 쪽 텍스트에 구멍이 있다 (OCR 중단).
그대로 쓰되 **빈 곳을 메우려 지어내지 않는다** — 사람에게 말한다.

**이어받기** — 중단된 문서를 이어받으려면 `get_document(id)` → `outline[].filled` 가
`false` 인 칸부터 돈다. 이미 채운 칸을 다시 쓰지 않는다.

## 3. ③ 조립 → 완료

플레이북의 조립 항목(도입·전환·마무리)을 손질하고 `put_document(id, status='done', ...)`.

**`done` 은 서버가 막는다** — 아래 셋 중 하나면 거절된다. 거절은 버그가 아니라 설계다.

| 거절 | 뜻 |
|---|---|
| 본문이 비어 있음 | 빈 문서가 완료로 뜨면 안 된다 |
| `sourceChapters` 가 비어 있음 | 출처를 잃으면 **영구히** 복원 못 한다 |
| `deck` 인데 `<section>` 0개 | 슬라이드쇼가 빈 화면, PDF 가 0쪽. **에러가 안 난다** |

완료 후 `get_document(id)` 로 `slides` 를 확인한다 — **아웃라인 칸 수와 같아야 한다.**
다르면 ②에서 칸을 쪼갰거나 합친 것이다 (계약 위반).

## 보고

끝나면 한 줄로 — 무엇을 몇 장으로 만들었고, **버린 장이 있으면 그것도.**
콘솔 경로(`책 상세 › 문서 탭`)를 알려 준다.

## 하지 않는 것

- **서버에 생성을 요청하기** — 그런 툴이 없다. 있으면 설계가 깨진 것이다
- `.pptx`·`.pdf` 를 직접 만들기 — deck 은 HTML 이고 PDF 는 콘솔 다운로드가 제로클라우드로 굽는다
- 플레이북을 안 읽고 쓰기 — 타입마다 금지사항이 다르다
- 아웃라인 승인을 건너뛰고 ②로 가기 — 그러면 3단이 1단이 되고 뒤쪽 장이 부실해진다
- `.knoverse/knowledge/` 에 쓰기 — 그건 `summarize`·`doc-create` 의 자리다. 이 스킬은 **제품 DB**
