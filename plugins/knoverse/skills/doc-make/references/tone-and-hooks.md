# 톤과 훅 — 듣는 사람에게 붙이는 법

> `tone` 옵션을 받을 때 본다.

## 톤 축

| `tone` | 무엇이 달라지나 | 어울리는 자리 |
|---|---|---|
| `plain` | 사실과 근거만. 비유 최소, 농담 없음 | 사내 설계 리뷰 · 의사결정 자료 |
| `light` (기본) | 익숙한 서비스 비유 1~2개, 가벼운 한 줄 **1~2회** | 스터디 발표 · 팀 공유 |
| `vivid` | 장면으로 열고, 비유를 축으로 끌고 간다. 농담 3~4회 | 콘퍼런스 · 사내 세미나 |

🔴 **`vivid` 라도 농담이 주장을 가리면 안 된다.** 업계 가이드가 공통으로 말하는 것 —
잘 놓인 하나는 분위기를 살리지만 **남발하면 신뢰를 깎는다.** 농담은 **슬라이드 사이**에 두고
주장 슬라이드 자체는 깨끗하게 둔다.

## 실제 서비스 사례 — "책 얘기" 에서 꺼내 온다

책 안 예시만 쓰면 발표가 **책 요약**으로 끝난다. 듣는 사람이 **매일 쓰는 것**에 붙인다.

| 개념 | 붙일 자리 (예) |
|---|---|
| 조건부 로직이 쌓인다 | 커머스 **쿠폰 중복 적용 규칙** — 조건이 분기마다 늘어난다 |
| 타입으로 분기하는 switch | **결제 수단**(카드·간편결제·포인트)별 처리 |
| 캡슐화·점진적 교체 | **API 버전 올리기** — 옛 필드와 새 필드를 같이 내려 주는 기간 |
| 단계 쪼개기 | **피드 랭킹** — 후보 추리기 / 점수 매기기 / 정렬이 다른 단계 |
| 테스트가 전제 | **배포 전 스모크** 없이 금요일 배포하는 기분 |

**고르는 규칙 셋**

1. **듣는 사람이 다 아는 것**으로 고른다 (인스타 피드·네이버 검색·배민 주문 같은)
2. 🔴 **지어내지 않는다.** 그 회사가 실제로 그렇게 구현했다고 **단정하지 않는다** —
   "이런 화면이라면" · "흔한 구조로는" 처럼 **가정으로** 말한다. 내부 구현을 아는 척하면 틀린다
3. 사례는 **개념을 여는 문**이지 본론이 아니다. 한 슬라이드를 넘기지 않는다

## 여는 훅 — 네 가지

| 훅 | 모양 | 쓸 때 |
|---|---|---|
| **질문** | "왜 '나중에' 는 오지 않는가?" | 모두가 겪은 일일 때 |
| **숫자** | "5.7%" 한 장 | 수치가 충격적일 때 |
| **장면** | "금요일 6시, 배포 버튼 앞에서" | 공감이 먼저 필요할 때 |
| **반전** | "이럴 줄 알았는데 아니었다" | 통념을 뒤집는 내용일 때 |

🔴 **표지 다음 장을 목차로 쓰지 않는다.** 흐름 슬라이드는 훅 **다음**이다 —
목차부터 띄우면 긴장이 생기기 전에 식는다.

## 닫는 법

마지막은 **요약이 아니라 행동**이다. 듣는 사람이 **내일 할 수 있는** 것 하나.

- ❌ "정리하면 리팩터링은 동작 보존과 작은 단계입니다"
- ⭕ "내일 우리 코드에서 타입으로 분기하는 switch 가 두 군데 이상인 곳을 찾아보세요"

## 금지

- 메타 발언 — "이번 발표에서는 …", "이 발표는 N장 안에서만 인용한다", 쪽 범위
- 인사말·맺음말 ("들어주셔서 감사합니다" 는 말로 하는 것이다)
- 근거 없는 업계 단정 ("대부분의 회사가…")
