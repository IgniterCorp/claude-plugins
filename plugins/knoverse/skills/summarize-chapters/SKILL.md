# summarize-chapters — 책 → 장별 요약 (제품 DB)

> 입력은 `get_chapter_text`, 출력은 `put_summary`. **서버는 요약을 만들지 않는다** —
> 이 세션이 만들고 서버는 저장·검증만 한다. [[doc-make]] 와 같은 계약이다.

## 왜 로컬인가

서버에도 AI 요약 경로가 있다(`POST /library/:id/summaries`). 쓰지 않는 이유 —

1. **과금.** 장마다 LLM 호출이 붙는다. 로컬 세션이 만들면 0 이다

덤으로 **품질 차이**가 있다. 서버 경로는 본문을 `MAX_BODY_CHARS = 24_000` 자로 자른다 —
60쪽짜리 장은 앞 1/3 만 보고 요약된다. 이 스킬은 전문을 읽는다.

## ⓪ 옵션을 **먼저 묻는다** — 건너뛰지 않는다

🔴 **이 단계가 없어서 한 번 실패했다.** 2026-10-04 에 리팩터링 2판 13장을 묻지 않고
`study` 로 만들었더니 전부 1,128~2,683자(평균 2,055자, **원문의 5.7%**)가 나왔고
*"너무 짧은 거 아님? 레벨 설정이 있긴 했나"* 를 들었다.
**고를 수 없는 것은 고른 적이 없는 것이다.**

세 가지를 **한 번에 보여 주고 고르게 한다.** 기본값을 말하되 그냥 쓰지 않는다.

| 옵션 | 값 | 무엇이 달라지나 |
|---|---|---|
| `output` | **`study`**(학습노트) · `review`(독후감) | 섹션 구성이 통째로 다르다 |
| `depth` | `brief`(요점) · **`standard`**(표준) · `deep`(깊게) | **장당 분량** — 아래 표 |
| `examples` | `none` · **`some`** · `many` | 코드·수식·사례를 얼마나 원문 그대로 옮기나 |

**장당 목표 분량** (정본은 `apps/core-api/src/summary/summary-options.ts`)

| `depth` | 장당 | 쓰임 |
|---|---|---|
| `brief` | 800~1,500자 | 읽은 책을 떠올리는 용도. 다시 공부할 생각이 없을 때 |
| `standard` | **2,500~4,500자** | 기본. 나중에 이걸 보고 복습한다 |
| `deep` | **5,000~9,000자** | 이걸로 **발표하거나 가르친다**. 코드·절차를 원문 그대로 싣는다 |

물을 때 **지금 책의 규모를 같이 말한다** — "13장 · 원문 469,000자" 처럼. 그래야 사람이
`deep` 이면 총 6.5만~11만 자라는 걸 알고 고른다.

🔴 **장마다 옵션을 바꾸지 않는다.** 한 책 안에서 섞이면 "왜 이 장만 짧지" 가 생긴다 —
예외적으로 짧은 장(3쪽짜리 서문 같은)은 **분량이 모자란 게 정상**이고, `put_summary` 응답의
`hint` 가 그걸 말해 준다. 힌트가 떴다고 억지로 늘리지 않는다.

## 절차

```
🔴 **요약은 버전이 쌓이지 않는다 — 덮어쓰면 이전 판이 사라진다.**
   `PUT …/summaries/<chapterId>` 는 **교체**(`replaced: true`)이고 이력이 없다.
   이미 요약이 있는 책을 **다른 성격으로 다시 쓸 때**(예: deep → 초보자용)는
   **덮어쓰기 전에 기존 판을 어딘가 영구 보관**한다. 스크래치패드는 세션이 끝나면 사라진다.
   (2026-10-08: 벤야민 17절을 초보자용으로 교체하며 deep 판을 아크 `data/` 에 남겼다)

🔴 **요약은 '쪽'에 붙는다** (같은 startPage 금지는 MCP 서버 지침 book-setup ②). 부(部) 간지 쪽이 없는 책에서
   "N부" 줄과 그 부의 첫 글을 같은 쪽에 두면 실제로 덮인다.
   (반대로 **목차를 통째로 갈아 끼워도 요약은 쪽에 붙어 살아남는다**)

⚠️ **MCP 없이 HTTP 로 확인할 거면 `GET /library/<itemId>/notes` 다** (`kind: "summary"` 로 걸러
   `pageNo`·`title`·`body` 를 읽는다). `GET …/summaries/<chapterId>` **라우트는 없다** — PUT 만 있다.
   404 본문이 `{"message":"Cannot GET …"}` 라 파서가 `body` 를 못 찾고 **0자로 집계한다**:
   다 써 놓고 "요약 0/16" 을 보게 된다 (2026-10-08 실제로 겪었다).

⓪ 옵션      output · depth · examples 를 사람에게 묻는다 (기본값을 그냥 쓰지 않는다)
① 명단      list_summaries → 장별 체크리스트를 **사람에게 보여 준다**
            (쪽 없는 장 = '할 수 없다' 를 함께 말한다)
② 장별      summarized=false 인 장마다:
              get_chapter_text → 형식대로 쓴다 → put_summary
            한 장 = 한 번 저장. 중단되면 거기서 이어진다
③ 확인      list_summaries 로 전 장 summarized=true 를 확인하고 콘솔 좌표를 준다
```

### ① 명단 — 보여 주고 시작한다

`list_summaries(itemId)` 가 장마다 준다:

| 필드 | 뜻 |
|---|---|
| `summarized` | 이미 요약이 있나 — `true` 면 **건너뛴다** (그게 곧 재개다) |
| `summarizable` | 요약을 붙일 자리가 있나. `false` = **시작 쪽이 없다** |
| `chars` · `generatedBy` | 있는 요약의 크기와 생산자 |

🔴 **`summarizable: false` 를 조용히 건너뛰지 않는다.** 쪽이 없으면 장 범위를 몰라 영원히
못 채운다 — 사람에게 "이 장들은 목차에 쪽이 없어 요약을 못 한다" 고 말하고,
`chapters/suggest-pages` 로 쪽을 먼저 채우자고 제안한다. 말없이 빼면 빠진 걸 아무도 모른다.

### ② 장별 — 한 장 쓰고 바로 저장한다

`get_chapter_text(itemId, chapterId)` 가 주는 것:

| `source` | 받은 것 | 어떻게 |
|---|---|---|
| `pageText` | 장 본문 원문 (수만 자) | 이걸 요약한다 |
| `summary` | **이미 요약이 있다** | ①에서 걸러졌어야 한다. 나왔으면 건너뛴다 |

`pages` 가 장 범위보다 적으면 **OCR 구멍**이다 — 그 장은 요약하지 말고 보고한다.
없는 쪽을 메워 쓰면 "읽은 것처럼 보이는" 틀린 요약이 된다.

**형식 정본은 서버 프롬프트다** —
`apps/core-api/src/summary/prompt.ts` 의 `buildPrompt`. 두 생산자가 같은 행에 쓰므로
모양이 갈라지면 노트 목록이 뒤섞인다. 2026-10-04 기준:

`output = study` (기술서·논문·자격증 기본)

```markdown
## 이 장의 핵심 (3~5줄)
## 개념 정리 — 용어마다 한 줄 정의
## 꼭 기억할 것 — 코드·수식·절차는 **원문 그대로** 옮긴다 (요약하지 마라)
## 스스로 확인 — 답이 본문에 있는 질문 3개
```

`output = review` (문학·에세이)

```markdown
## 무슨 이야기였나 (5줄 이내)
## 인상 깊은 대목 — 짧은 인용과 왜 그런지
## 남는 생각
```

### `depth` 가 **무엇을 더 쓰는지**를 정한다 — 같은 글을 늘리는 게 아니다

> 🔴 정본은 서버 코드다 — `prompt.ts` 의 `DEPTH_RULES`·`EXAMPLES_RULES`, 분량은 `summary-options.ts` 의
> `DEPTH_CHARS` (2026-10-08 부터 서버 `POST /summaries` 도 같은 표를 읽는다). 아래 표는 그 사본이다 —
> 갈라지면 서버 코드가 이긴다.

| | `brief` | `standard` | `deep` |
|---|---|---|---|
| 이 장의 핵심 | 3줄 | 3~5줄 | 5줄 + **이 장이 뒤집는 통념** 한 줄 |
| 개념 정리 | 핵심 용어 3~5개 | 나오는 용어 전부 한 줄 정의 | 〃 + **왜 그렇게 부르나**·헷갈리는 이웃 개념과의 차이 |
| 꼭 기억할 것 | 한 덩어리 | 2~4덩어리 | **절(節)마다 한 덩어리** — 코드·절차·인용을 원문 그대로 |
| 추가 섹션 | — | — | **`## 절차·표`** (책이 단계나 표로 준 것을 그대로 옮긴다)<br>**`## 저자가 선을 긋는 곳`** (저자가 명시적으로 반대·한계를 말한 대목) |
| 스스로 확인 | 2개 | 3개 | 5개 — 답이 본문 어디에 있는지까지 |

🔴 **`deep` 에서 늘리는 것은 원문의 밀도지 내 문장이 아니다.** 형용사를 붙이거나 같은 말을
다시 쓰지 않는다. 늘릴 재료는 **절 단위로 더 내려가는 것**과 **원문 그대로 옮기는 것** 둘뿐이다.

🔴 **`examples` 가 코드 분량을 정한다.** `many` 면 책의 코드 예시를 **돌아가는 상태로** 싣는다
(`...` 로 줄이면 안 돌아가는 코드가 된다). `none` 이면 코드 블록을 아예 넣지 않는다.

**공통 규칙은 knoverse MCP 서버 지침의 "요약 규칙"을 따른다** (지어내지 않기·근거 쪽과 원문 인용·OCR·적용 금지).

- `study` 는 **압축이 아니라 재구성**이다 — 줄이는 게 목적이면 코드·용어·절차가 사라지고
  목차만 남는다. 앞 장 요약을 읽어 흐름이 이어지면 연결한다

저장: `put_summary(itemId, chapterId, body, options)` — **장마다 한 번.** ⓪에서 고른 옵션을
**매번 함께** 보낸다(재현의 근거이자, 응답 `hint` 로 분량을 바로 확인하는 길이다).
모르는 키·오타는 **거절된다** — 조용히 기본값으로 떨어지면 고른 적 없는 설정이 된다. 전부 모아서 마지막에
저장하지 않는다 (중간에 끊기면 전부 잃는다). 같은 장에 다시 부르면 덮어쓴다(`replaced: true`).

### ③ 확인

`list_summaries` 로 전 장 `summarized: true` 를 **tool 결과로** 확인한다. 그리고 좌표를 준다 —
콘솔 책 상세의 파이프라인 ③ 장별 요약(장마다 글자 수·생산자가 뜬다)과 노트 목록(전문).

## 실측 — 리팩터링 2판 13장 (2026-10-04)

첫 완주 기록. 다음 책의 기대치다.

| | |
|---|---|
| 장 | 13 / 13 (중복 0 — `summaries 13 = chapters 13`) |
| 분량 | 26,714자 · 장당 1,128 ~ 2,683자 |
| 입력 | 전부 `pageText` (요약이 없었으니 당연) · 가장 큰 장 76,715자 |
| 하류 효과 | `doc-make` 입력이 같은 7장 기준 274,163자 → 16,490자 (**17배**) |

**장당 1,500~2,500자가 쓸 만한 폭이었다.** 더 줄이면 `꼭 기억할 것` 의 코드·인용이 빠지고,
더 늘리면 원문을 옮기는 쪽에 가까워진다. 카탈로그형 장(6·11·12장)은 **기법 표**가 들어가
자연히 길어진다 — 그건 정상이다.

## 다음

요약이 쌓이면 `get_chapter_text` 가 **요약을 먼저** 준다(`source: summary`). 그래서
[[doc-make]] 가 훨씬 적은 입력으로 돈다 — 발표자료·핸드아웃·독후감이 그 위에 올라간다.

## 금지

- **옵션을 안 묻고 시작하기** — 이 스킬이 한 번 실패한 지점이다
- 전부 만들고 마지막에 한 번 저장 — 끊기면 전부 잃는다
- `summarizable: false` 를 말없이 건너뛰기 — 영원히 안 채워진다
- 이미 `summarized: true` 인 장을 다시 만들기 (`--force` 를 사람이 말했을 때만)
- `source: pageText` 인데 `pages` 가 범위보다 적은 장을 그냥 요약하기 — OCR 구멍이다
- 파일로 쓰기 — 정본은 제품 DB 다 (파일 기반은 구 `knoverse:summarize` 의 세계다)

## 함정

- **`chapters/flat` 은 장 id 를 안 준다** (읽기 화면용이라 `title`·`startPage`·`level` 만).
  장 id 는 `list_summaries` 나 `get_book_context` 에서 온다
- 장 본문이 수만 자다. **전부 컨텍스트에 띄우지 않는다** — 절 머리와 각 절 앞머리를 뽑아
  구조를 먼저 보고, 필요한 절만 깊이 읽는다. 카탈로그형 책은 **구조 자체가 내용**이다
- OCR 본문이라 기법 이름 옆 각주 번호가 깨져 붙는다(`함수 추출하기*'*`). **기법 이름은 살리고
  깨진 기호는 버린다** — 원문 그대로 옮기라는 규칙은 코드·인용에 걸리는 것이지 OCR 잡음이 아니다
